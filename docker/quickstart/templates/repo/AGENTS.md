# Proving the laws of {PROJECT}

This repository was assembled by QuickProof (`qp assemble`). It holds a piece of C code, the laws it must obey
(one C harness per law, in `harness/`) and, for each law, a Coq theorem that is not proved yet. Your task is to
prove these theorems. Nothing you write is trusted: the work counts only when `qp verify` accepts it (see
"Done" below), and it checks everything on a fresh clone.

## The theorems

{THEOREMS}

For each law `LAW` the file `src/contracts/LAW.v` ends with

    Theorem LAW : harness_safe whole_prog.
    Proof.
    Admitted.

`whole_prog` is the harness `harness/LAW.c` linked with the code it calls. `harness_safe whole_prog` is VST's
whole-program judgement for that program. Read through VST's adequacy theorem, which connects such a judgement with
runs, it says that no run of that program has undefined behaviour in CompCert's C semantics (x86-64), for every value
the `nondet_*` calls may return (`quickproof/docs/GUARANTEES.md` has the exact meaning). A failing `gp_assert` is
undefined behaviour, so the theorem says that every assertion holds. It also rules out out-of-bounds accesses, uses
after free, signed overflow and the like. `gp_assume(c)` cuts off the runs where `c` is false. The meaning of each
name is in `quickproof/coq/QuickProof/Contract.v` (the theorem) and `quickproof/coq/QuickProof/Env.v` (the
specifications of `nondet_*`, `gp_assert`, `gp_assume`, `malloc`, `free`). Specs write these two as `qp_assert` and
`qp_assume`, macros for `gp_assert` and `gp_assume`; the Clight, `Env.v` and older specs use the `gp_` names.

## Where things are

- `harness/LAW.c`: the law. Read it first: the theorem is exactly this program.
- The code under test: {CODE_FILES}.
- `src/contracts/LAW.v`: the contract. Everything down to the banner `THE THEOREM` is generated: the Clight
  program of the harness (Clight is the C dialect that CompCert and VST work with), the link `whole_prog`, a
  check of its undefined globals. Then the theorem.
- The Clight of each C file, generated by clightgen and never edited: `src/<dir>/code.v` (for example the
  function `f` of the code is `f_f` there, its name is `_f`, its local `i` is `_i`, and clightgen's temporaries
  are `_t'1`, `_t'2`, ...). Each C file is a unit; the units of the project are {UNITS}. Each unit has a module
  in `src/units/` that defines the unit's `CS : compspecs` and its program `qp`. The comment at the top of a
  contract file says which units its law links: only the functions of those are in `whole_prog`.
- `_CoqProject`: `src/` is the Coq library `{LOGICAL}`, so `src/proof/Foo.v` is `{LOGICAL}.proof.Foo`.
- `quickproof/`: the framework at the commit the proof is checked with.
- Worked examples to read: `quickproof/examples/` (see its README.md). Each has the code, the law in
  `harness/`, and in `proof/` the files its proof adds to a repository like this one: a specification and a
  body proof per C function in `proof/src/proof/`, the proof of `main` and of the theorem in
  `proof/src/contracts/`.
  - `rle`: a loop over a byte buffer; a harness with `malloc`, `nondet_bytes`, `qp_assume`, `qp_assert`, `free`.
  - `adler32`: a functional model in Coq, a buffer split in two, three calls in one harness.
  - `find_byte`: a search loop that exits early; the smallest complete example.

## What you may change

- Add Coq files under `src/` (put specifications and lemmas in `src/proof/`).
- In `src/contracts/LAW.v`: add your proof between the generated part and the banner `THE THEOREM`, and replace
  the `Admitted.` of the theorem by a proof (usually `Proof. exact LAW_proved. Qed.`).

Nothing else. In particular:

- Never change the statement of a theorem, anything above `THE THEOREM`, the harnesses, the C code,
  `quickproof/`, `quickproof.conf`, `_CoqProject`, `.gitmodules`, or any generated `code.v` or `src/units/*.v`.
- Never use `Admitted`, `admit`, `Axiom`, `Parameter`, `Conjecture`, or anything else that assumes what it
  should prove. Only the standard axioms and VST's malloc library are accepted.
- Never rewrite git history, move or delete the tag `contract`, or commit changes outside `src/` other than
  notes such as `COUNTEREXAMPLE.md`.
- Do not weaken a specification until it says nothing useful about the code: the theorem is fixed, so a
  specification only has to be strong enough to prove it, but it must be true of the code.

## How to prove a law

1. Read the harness and the code. Find which C functions the harness calls, directly and indirectly.
2. For each of them, write a VST specification in `src/proof/<Name>.v`, then prove its body. The file starts
   like the examples:

       Require Import VST.floyd.proofauto.
       Require Import VST.floyd.VSU.
       Require {LOGICAL}.units.<Unit>.
       Require Import {LOGICAL}.<dir>.code.
       #[export] Instance CS : compspecs := {LOGICAL}.units.<Unit>.CS.
       Definition Vprog : varspecs. mk_varspecs {LOGICAL}.<dir>.code.prog. Defined.

   A specification:

       Definition f_spec :=
         DECLARE _f
         WITH p: val, sh: share, bs: list Z
         PRE [ tptr tuchar, tulong ]
           PROP (readable_share sh; Zlength bs <= Int64.max_unsigned;
                 Forall (fun b => 0 <= b <= Byte.max_unsigned) bs)
           PARAMS (p; Vlong (Int64.repr (Zlength bs)))
           SEP (data_at sh (tarray tuchar (Zlength bs)) (map (fun b => Vint (Int.repr b)) bs) p)
         POST [ tulong ]
           EX r: Z,
           PROP (0 <= r <= Zlength bs)
           RETURN (Vlong (Int64.repr r))
           SEP (data_at sh (tarray tuchar (Zlength bs)) (map (fun b => Vint (Int.repr b)) bs) p).
       Definition Gprog : funspecs := [f_spec].
       Lemma body_f: semax_body Vprog Gprog f_f f_spec.
       Proof. start_function. ... Qed.

   C types in VST: `size_t` is `tulong` with values `Vlong (Int64.repr n)`; `uint8_t` is `tuchar` and `int`
   is `tint`, both with values `Vint (Int.repr n)`; `uint32_t` is `tuint`; a pointer to `uint8_t` is
   `tptr tuchar`. Memory: `data_at sh t v p` (initialised), `data_at_ sh t p` (any contents).
3. Write every loop invariant before you prove the loop. Most failed attempts come from a weak invariant: it
   must give the bounds every array access needs and keep what the postcondition needs. Use `forward_loop
   Inv break: Post`, or `forward_for_simple_bound n Inv` for a counting `for` loop. `forward_if` needs a join
   postcondition when both branches continue.
4. Prove `main` in the contract file against `main_spec_std p` (with `Definition p := whole_prog.`): start with
   `start_function. sep_apply (create_mem_mgr gv).`, then one `forward_call` per call. The environment
   functions have the specifications `nondet_size_spec`, `nondet_u8_spec`, `nondet_u32_spec`,
   `nondet_bytes_spec`, `gp_assume_spec`, `gp_assert_spec`, and `malloc_spec'`/`free_spec'` under the names
   `_quickproof_malloc` and `_quickproof_free`. A `gp_assert` call leaves the obligation that its condition is
   not zero: that is where the law is proved. The examples show the whole pattern, including the compspecs of
   `whole_prog` and `change_composite_env` from the unit's `CS`.
5. Assemble the theorem as the examples do:

       Lemma LAW_proved : harness_safe whole_prog.
       Proof.
         harness_safe_by_specs CS G main_post_TT.
         - reflexivity.
         - entry_shared (semax_body_main_std _ _ p _ _ body_main eq_refl).
           entry_shared F.body_f.                      (one per C function of whole_prog)
           entry_external (@external_ok_size CS).      (one per environment function it calls)
           ...
           apply Forall_nil.
       Qed.

   `G` lists `main`'s spec (`QPmain_spec_ext' p tt main_post_TT`), your function specs and the environment specs.

Useful tactics: `forward`, `forward_call`, `forward_if`, `forward_loop`, `Intros`, `Exists`, `entailer!`,
`cancel`, `sep_apply`, `list_solve`, `rep_lia`, `lia`, `Znth_map`, `Int64.unsigned_repr`. Unsigned comparisons
of `size_t` appear as `Int64.ltu`; the examples show how to turn them into `<` on `Z`.

## Checking your work

Run these in this repository (inside the QuickProof container, see the last section otherwise):

- `qpdemo build {PROJECT}` compiles everything (`coq_makefile -f _CoqProject -o CoqMakefile` and `make`) and
  lists what is still `Admitted`. Run it once before using the interactive tools: they need the compiled
  dependencies, and after you change a file that another one imports, build again.
- The MCP server `rocq` (rocq-mcp) gives the goals step by step, which is much faster than recompiling:
  - `rocq_start(file=..., theorem=...)` opens a proof and shows its goals; it returns a `state_id`;
  - `rocq_check(body="start_function. forward.", from_state=...)` runs tactics and shows the new goals;
  - `rocq_step_multi(tactics=[...], from_state=...)` tries several tactics at once;
  - `rocq_query(command="Search Int64.ltu.", file=...)` searches, `Check`s and `Print`s in a file's context;
  - `rocq_compile_file(file=..., keep_vo=true)` compiles one file and keeps its `.vo` for the files that import
    it (without `keep_vo` it deletes the `.vo`, and those files need `qpdemo build` again);
  - `rocq_toc(file=...)` lists the definitions of a file.
  Paths may be absolute or relative to this repository. `rocq_verify` and `rocq_assumptions` are not the
  acceptance check here; `qp verify` is.
- Without the MCP server, put `Show.` in a proof and compile to print the goals.

## Done

The work is done when `qpdemo verify {PROJECT}` prints `PASS`. It commits your changes under `src/` and runs
`qp verify`, which on a fresh clone

- rebuilds the Clight from the C code and requires it to be identical to the committed files;
- requires that nothing but proof sources (`src/**.v`) and notes changed since the commit tagged `contract`;
- builds the contracts and the proof, and compares the statement of every theorem, as Coq elaborates it, with
  the one at the `contract` commit;
- requires `Print Assumptions` of every theorem to name only the standard axioms and VST's malloc library;
- fails if the proof's own sources contain any `Admitted`, `admit`, `Axiom`, `Parameter` or `Conjecture`, even
  in a lemma that no theorem uses.

Any other claim of success does not count. Run it at the end, and again after any change.

## If the law is false

A law can be false. If a proof gets stuck because the code really can break the law, look for a concrete input
that does it (`qpdemo check {PROJECT}` runs the law natively and under CompCert's interpreter), write it with
the reason into `COUNTEREXAMPLE.md`, and stop. That is a result. Never weaken the law, the harness or the code
to get around it.

## Running outside the container

If you run on the host, with the repository shared with a running QuickProof container, run the commands of
"Checking your work" through the container: `docker exec <container> qpdemo build {PROJECT}`, and connect to
the MCP server with `docker exec -i <container> rocq-mcp` (the person who set this up knows the container's
name). The paths are the same on both sides when the work directory is mounted at the same path.
